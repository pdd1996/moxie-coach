# S1-F1 实现计划 — 题库元数据与仪表盘（运行期合并方案）

## Context

S0 三件地基已落地。现在做 S1-F1：让题单/仪表盘展示**全部 151 题元数据**并按真数据聚合复习队列/进度/建议新题。

**现状的鸿沟**：`src/data/problems.json` 已有 151 条元数据，但运行期 app 用的是 `seed.ts`（40 题、含完整状态）→ 落进 `db.json.problems`（完整 `Problem` 对象）。所以题单/仪表盘现在只展示 ~40 题。S1-F1 要求「已录入题全展示、分组正确」。

**已确认方案（用户拍板）**：运行期合并——`problems.json` 作为只读元数据在运行期读入；`db.json.problems` 只存**用户状态**（status/srsLevel/nextReviewAt/history/note/lastCode/lastLang/statement/skeleton/solution/testCases/entry）；store 按 id 合并成 `Problem[]`。元数据日后改了（补 pattern/signal、加方法论代表题）现有用户立刻生效，无需重置 db。代价：需改已落地的 `store.ts` + `seed.ts` + `middleware.ts` 的 seed 形状（db 形状从「完整 Problem[]」变「用户状态[]」）。

## 数据模型变更

**`problems.json`（只读元数据，`ProblemMeta[]`）**——已存在 151 条，补 5 条：
- 加 `206 反转链表`、`704 二分查找`、`347 前 K 个高频元素`、`78 子集`（方法论代表题，见 `套路映射.md`，canonical 非 optional）
- 加 `1114 按序打印`（多线程，`optional: true`，stage 2，pattern `多线程`）→ 满足「多线程题标记选做」验收
- 合计 156 条。meta 字段：id/title/slug/difficulty/stage/pattern/signal?/optional?（**不含 entry**，entry 由 F2 贴题时解析存入 db，见 S2-F2）

**`db.json.problems`（用户状态，新形状）**——数组，每条只含用户字段 + `id`：
```
{ id, status, history, note?, hintCard?, srsLevel?, nextReviewAt?,
  lastCode?, lastLang?, statement?, skeleton?, solution?, testCases?, entry? }
```
未触碰的题不在 db 里，合并时补默认值（`status:'new'`、`history:[]`、`testCases:[]`）。

新增类型 `ProblemUserState`（`src/lib/types.ts`）；`Problem = ProblemMeta & ProblemUserState`（`testCases` 在合并层保证非空，故 `Problem.testCases` 仍 required）。

## srs.ts 纯函数口径（对齐 spec 实现要点）

- `todayStr()`：本地日期 `YYYY-MM-DD`（放 `src/lib/utils.ts` 或 srs.ts；用 `new Date()` 取本地日，非 UTC）
- `reviewQueue(problems, today)`：`nextReviewAt <= today` 且 `status ∈ {learned, pending-review, self-solved, reviewing}`；按 `today - nextReviewAt` **天数降序**（逾期不惩罚 = 仅排序不加权）
- `suggestedNew(problems)`：阶段 1→4 扫，**第一个仍含 `status==='new' && !optional` 的阶段**→ 取该阶段第一道 new（「阶段一未做完前不跨阶段」）
- `stageProgress(problems)`：每阶段 `done = status ∈ {self-solved,learned,reviewing,mastered}` 计数、`total = !optional` 计数
- `patternStats(problems)`：按 `pattern.split('（')[0]` 聚合，`total>=2`，按 done 降序
